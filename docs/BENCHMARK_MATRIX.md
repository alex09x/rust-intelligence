## Notes

- `-32801` is `ContentModified`: the server reports that re-analysis is in progress.
- RIDX `textDocument/documentSymbol` returns `[]` for files not opened via `didOpen`; the benchmark does not open files before symbol queries, so the RIDX documentSymbol latency is not comparable with rust-analyzer's.
- The readiness canary issues `textDocument/definition` on the first three sampled positions, so the rust-analyzer cold latency for those three positions out of 300 is measured on a warm cache.
- `a` counts non-empty answers, `b` empty answers (`null`, `[]`, empty hover), `c` failed scenarios; `errors` counts error responses, which can exceed `c` because a scenario sends several requests.
- serde: the corpus has no committed `Cargo.lock`. The generated lockfile resolved a registry `serde_derive` of a newer version next to the workspace one, and `trybuild` in `test_suite` then failed to compile; the lockfile was regenerated with `serde_derive` unified to the workspace version. Its sha256 is recorded as `corpus_lockfile_sha256`.
- All five runs use RIDX commit `6ce1fa9`. The later commits `7913226` and `ec21213` change the `typeHierarchy/subtypes` and `typeHierarchy/supertypes` reference fallback; the 42 bevy `typeHierarchy/subtypes` timeouts in this run are the behaviour of `6ce1fa9`.
- Indexes were built with the driver recorded as `driver_hash` (`driver_build_commit`), which can be older than the RIDX commit. Between driver build commit `cdf975d` and RIDX commit `6ce1fa9` the driver changed only in `build.rs` (link search path) and `ridx-format` only in reader-side workspace code, so the index contents do not depend on the newer commit.

## Known harness defects (fixed, in commit order)

- `18088fc`: `$/cancelRequest` scenarios reused numeric ids that collided with query ids; string ids are used since this commit.
- `b704408`: synchronization scenarios left overlays open, so later queries ran against modified buffers; each scenario now opens and closes its own document.
- `9ebb233`: queries started as soon as rust-analyzer reported `quiescent`, before its `$/progress` work was finished; the runner now waits for all progress tokens to end.
- `e23e23d`: rust-analyzer starts a second indexing pass after the first `quiescent`; readiness is now confirmed by a `textDocument/definition` canary on the first three sampled positions (two consecutive non-empty answers).
- `d3b7810`: the synchronization block (ids 8-14) makes rust-analyzer reload the workspace and answer `textDocument/definition` with empty results for a few seconds (measured on tokio: 229/300 non-empty before the block, 0/300 right after, 229/300 sixty seconds later); the runner now re-establishes readiness before the first query method.
- `c4667d9`: the client wrote requests to the server's stdin while holding the lock its reader thread needed, so a server blocked on a full stdout pipe and the client blocked on a full stdin pipe waited for each other; stdin writes now use a separate lock.
- `1d5d2ca`: a request that hit the client timeout was never cancelled, so the server kept computing it and delayed the first requests of the next method (observed on bevy: about 20 s per `typeHierarchy/subtypes` request against a 2 s timeout); the client now sends `$/cancelRequest` on timeout and waits for outstanding answers before each method.
